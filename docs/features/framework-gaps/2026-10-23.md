# Framework gaps, found by building stages — 23 October 2026

Each stage we build is a test of the framework. When a chapter has to work around the
framework, or rebuilds something every interactive chapter will need, that is a gap. This
file records every gap found on this date: where it was found, what it costs today, and what
the framework should offer instead. It also records places where the same idea is done in
slightly different ways across chapters (consistency), and real bugs found along the way.

**How to use this file later.** Pick an item, build it, then change its status here from
`proposed` to `built` with the date and the files changed. When a new stage finds new gaps,
add a new dated file (`YYYY-MM-DD.md`) in this folder rather than rewriting this one, and list
any items carried over. The process is in [§10](#10-how-this-ledger-grows).

The first source of these findings is the soft chapter:
`lerpettes/content/physics-engine/particles/code/soft/js/` (`index.ts`, `jelly.ts`, `web.ts`,
`plate.ts`). It contains a working version of almost every proposal below, written by hand,
so it is the reference implementation to lift code from.

## 01 · The rule that decides where a feature goes

A chapter's code arrives in one of two ways:

- **Module** (`code/<id>/js/index.ts`): written by the author, compiled by Vite, can import
  anything (framework helpers, three.js, picture files via `new URL(..., import.meta.url)`,
  `import.meta.glob`).
- **Code box** (a ` ```lerpit src/step.js``` ` block): edited by the reader, compiled in the
  browser by `compileJs`. Its `require` resolves **only among its own open tabs**. It cannot
  import framework helpers, three.js or a picture file, and `import.meta` is a syntax error
  inside the compiled `Function`.

So **everything a reader can use must arrive as an argument**: `ctx` or the panel's drawing
object (`sketch`). That gives three tiers:

| Tier | Where | Who can use it | Rule |
|---|---|---|---|
| **Tier 1 · core** | on `ctx` | everyone, readers included | Small, additive changes to the framework contract; old chapters keep working. |
| **Tier 2 · sketch** | new calls on `sketch` | everyone (the object is handed in) | New drawing calls. |
| **Tier 3 · helpers** | importable modules (`@lerpit/framework/*`, `lerpettes/libs/*`) | authored modules only | Plain-data helpers like `Trail`. Physics stays visible in the chapter, because the physics is the lesson. |

## 03 · Pointer input (G1–G4, G10) — Tier 1

Today a chapter reads `ctx.input = { x, y, down, inside }` once per frame (the step gets the
active panel's input). The soft chapter needed four things it does not give.

**Where it lives today:** `lerpettes/framework/runtimes/createChapterRuntime.ts` (the pointer
listeners, `pointerleave` clearing `down`, `STEP_DT = 1/60` at line ~40).
`lerpettes/framework/runtimes/frameLoop.ts:45` has `MAX_FRAME_SECONDS = 1/30`.

### 3a · Pixels in, units out (G1)

Positions arrive in panel pixels (origin top left, y down). Chapters simulate and draw in units
(origin in the middle, x from −1 to 1, y up, `halfHeight = h/w`). Every pointer chapter
converts by hand. In the soft chapter:

```ts
// today: index.ts, by hand
const unit = ctx.view.width / 2 || 1;
const x = ctx.input.x / unit - 1;
const y = ctx.view.halfHeight - ctx.input.y / unit;
```

```ts
// proposed: the framework converts once
const { ux, uy } = ctx.input;
// x, y stay in pixels for anything laid out against the panel's edges
```

### 3b · A quick tap falls between two frames (G2)

The framework sets `down` on `pointerdown` and clears it on `pointerup`. A chapter samples it
once per frame (~16.7 ms). A tap shorter than the gap between frames is never seen as down,
so the press is lost. The soft chapter finds a press by comparing `down` with last frame's
value — the same bug:

```ts
// today
if (ctx.input.down && !s.down) press(s, x, y);
s.down = ctx.input.down;
```

```ts
// proposed: latched edges, set by the event, cleared after the next step reads them
if (ctx.input.pressed) press(s, ctx.input.ux, ctx.input.uy);
if (ctx.input.released) release(s);
// a tap shorter than a frame sets both in the same step
```

### 3c · Dragging past the panel's edge (G3)

The framework listens on the panel's box with no capture and clears `down` on
`pointerleave`. Dragging the jelly or the plate past the edge ends the drag the instant the
pointer crosses it. Proposed: `setPointerCapture` on press, so moves and the release keep
arriving wherever the pointer goes; `inside` becomes false and the chapter decides what to do
with a point outside (the soft chapter already clamps the plate to its bounds).

### 3d · Touch scrolls instead of dragging (G4)

Nothing sets `touch-action: none` on the stage, so on a phone a finger drag on the panel is
taken by the browser as a scroll. The browser then fires `pointercancel`, which the framework
ignores, and `down` can stay true after the finger lifts.

- Fix: `touch-action: none` + a `pointercancel` handler that acts as a release + first finger
  only (a second finger is ignored until the first lifts; no jump between fingers).
- **Trade-off:** it changes scrolling. A reader who puts a finger on the panel to scroll the
  article would drag the scene instead. So turn it on **only for panels whose chapter reads the
  pointer**: either a flag in `createStage({ input: true })`, or detect the first read of
  `ctx.input`. Panels that never read the pointer keep normal scrolling.
- This is outside `code/soft`, which is why the soft chapter does not fix it itself.

### Keyboard (G10)

Anything draggable needs a keyboard way to move it (accessibility). The scratchpad moved the
plate with arrow keys; the framework has no keyboard input, so the chapter could not offer it.
Proposed: `ctx.input.keys` (a set of held keys) plus latched key presses, with the panel
focusable.

### The proposed contract (additive)

```ts
export type PointerState = {
  x: number; y: number;           // pixels, as today
  down: boolean; inside: boolean; // as today
  ux: number; uy: number;         // the same point in units (−1..1 across, y up)
  pressed: boolean;               // a press happened since the last step (latched)
  released: boolean;              // a release (or cancel) happened since the last step
  pressX: number; pressY: number; // where the current or last press began, in units
  kind: 'mouse' | 'pen' | 'touch';// so a chapter can widen hit areas for fingers
};
```

Every field chapters use today keeps its meaning. The flags are cleared after `step` reads
them, so a paused chapter keeps them until it runs again.

### Edge cases the pointer work must handle (turn each into a test)

- **A tap inside one frame:** `pressed` and `released` both set in the same step.
- **A second finger:** ignored until the first lifts.
- **Leaving the panel mid-drag:** moves keep arriving; `inside` false; the release still arrives.
- **Pause mid-drag:** flags wait for the next step; releasing while paused ends the drag when
  the chapter resumes.
- **Restart or switching chapter mid-drag:** pointer state resets; no drag carries over.
- **Panel resizes mid-drag:** unit coordinates follow the new size from the next event.
- **Keyboard:** see G10.
- **Readers scrolling on a phone:** panels that don't read the pointer keep normal scrolling.

## 04 · Assets (G5) — Tier 1

The soft chapter loads `stapler.png` and `stapler-plate.png` with
`new URL('../stapler.png', import.meta.url)`, and its config with
`import.meta.glob('../stapler-config.json', { eager: true, import: 'default' })` (which also
needed `/// <reference types="vite/client" />` for `tsc`). That works because Vite rewrites
it in a module. In a code box, `import.meta` belongs to the browser-compiled `Function` and is
a syntax error, so a reader's code cannot load the same picture.

The runtime already knows the chapter's asset path — `resolveAssetUrl` in the runtime context
(`lerpettes/framework/types.ts:14`) — but chapters are never given it. The published site
already serves every file in a lerpette's folder under `/assets/lerpettes/`.

```ts
// today, in the soft chapter
const PICTURE = new URL('../stapler.png', import.meta.url).href;
let assets: Promise<Assets> | null = null;   // a cache by hand
const load = (src) => new Promise((ok, fail) => {
  const img = new Image(); img.onload = () => ok(img);
  img.onerror = () => fail(…); img.src = src;
});
```

```ts
// proposed
async setup(s, ctx) {
  const img = await ctx.loadImage('stapler.png');
  const cfg = await ctx.loadJson('stapler-config.json', { optional: true }); // null when absent
}
```

- Cache loaded images per page so a restart does not download them again.
- **Risk:** a missing file must fail loudly, with the file's name in the stage caption (the
  framework already does this for thrown errors), not as a blank panel.
- Requires `setup` to be allowed to be async (check what the runtime does today).

## 05 · Images and textured meshes (G6) — Tier 2

The sketch draws everything as triangles in **one buffer**, in call order, with **one
texture**: the glyph atlas for text. A picture cannot go into it. So the soft chapter built its
own three.js meshes for the plate and the jelly (`MeshBasicMaterial`, transparent, no depth
test, double-sided, SRGB), gave them `renderOrder` −2 and −1 so they draw before the sketch
(renderOrder 0), transformed units to pixels itself, and disposed of them by hand in
`dispose`.

The cost is not only ~70 lines: **a picture can only ever sit under the sketch's lines**,
never above them, and two pictures cannot have drawing interleaved between them.

Proposed: one draw list, split into batches whenever the texture changes; batches draw in
order. The common case (no pictures) stays one draw call, as today. Pictures upload once and
are kept until the run ends.

```ts
// a picture, its corners in units, drawn where the call is in the list
sketch.image(img, x1, y1, x2, y2, { alpha?: number });
// triangles cut from a picture: points in units, uv 0..1 across and down
sketch.mesh(points, tris, uv, img, { alpha?: number });
```

Example order: `line` (grid, atlas batch A) → `image(plate)` (batch B) →
`mesh(jelly)` (batch C) → `line` (web threads, atlas batch D).

**Replaces** in the soft chapter: the plate quad, the jelly mesh, the materials, the render
order, the unit-to-pixel transforms and the disposal map (`viewport2d.build` and most of
`draw`). File to change: `lerpettes/framework/panels/viewport2d/sketch2d.ts` (has uncommitted
user edits as of this date).

## 06 · Picking and dragging (G7) — Tier 3

Every draggable scene answers the same question on each press: what is under the pointer?
The soft chapter's rule (in `press()` in `index.ts`):

1. Within **14 reference px** of a free mass → pull that mass.
2. **Inside the jelly** (triangle test over `jelly.tris`) → pull the nearest free mass and
   **keep the offset**, so it does not jump to the pointer. (Needed because with Rings = 2 the
   web is coarse and a press inside a cell can be >36 px from every mass — this was a real bug
   during development: "nothing moves".)
3. **On the plate** (alpha test against the plate layer) → drag the plate, clamped to bounds
   in x and y.
4. Else, the nearest mass within **36 reference px**.

The rule is the chapter's. The plumbing is not: hit-testing in reference pixels (so a target
is as easy to hit on a phone as on a desktop), keeping the offset, holding the target through
the drag, clamping to bounds, smoothing. A plain-data helper like `Trail`:

```ts
import { Drag } from '@lerpit/framework/interact';

state: { drag: Drag.create() },
step(s, dt, ctx) {
  Drag.update(s.drag, ctx.input, [
    { id: 'mass',  near: s.jelly.p, within: 14 },                 // reference pixels
    { id: 'plate', hit: (x, y) => onPlate(s, x, y), bounds: s.bounds },
    { id: 'mass',  inside: s.jelly.tris, near: s.jelly.p, keepOffset: true },
  ]);
  // s.drag.target = { id: 'plate' } | { id: 'mass', index: 12 } | null
  // s.drag.x, s.drag.y: where the target should go, offset kept, smoothed, in bounds
}
```

Depends on G1/G2 (units and latched presses). `kind === 'touch'` could widen `within`.

## 07 · The mouse spring (G8) — Tier 3

The naive drag sets the held mass's position to the pointer. In a stiff spring network that is
a disaster: pointer events arrive unevenly between frames, so the mass teleports by uneven
amounts, each jump an impulse into stiff springs; a fast flick moves one mass a long way in one
step and turns triangles inside out.

The soft chapter's fix (`grab()` in `jelly.ts`, the hand update in `index.ts` step):

1. **Smooth the pointer:** the hand follows the pointer with a ~25 ms time constant.
2. **Hold a patch:** the pressed mass and its neighbours within ~1.1 thread lengths each get a
   spring to the hand (stiffness = the sum of the springs joined to that mass), not one mass
   alone.
3. **Critically damped:** `c = 2√(k·m)`, so the patch arrives without overshoot.
4. **Cap the lead:** however far the hand runs, the pull acts as if it were at most **0.4 of a
   thread** away.

Cloth, ropes, rigid bodies and any future mass-spring stage will need this. It belongs in a
physics helper, not the framework core, because it adds forces, and forces must stay visible
in the chapter's code:

```ts
import { Hand } from '@lerpit/libs/physics/hand';

s.hand = Hand.grab(s.masses, s.springs, index, { k: s.k }); // on press
Hand.follow(s.hand, ctx.input.ux, ctx.input.uy, dt);       // each frame, before sub-steps
Hand.applyForces(s.hand, s.masses, t);                     // inside each sub-step
```

`lerpettes/libs/physics` already exists.

## 08 · What should NOT move into the framework

- **Tracing a web from a picture** (`web.ts`, ~420 lines: outline trace, centre search, taut
  spokes, merging, relaxing, untangling). Specific to one idea. If a second chapter needs it
  (cloth cut from a picture), move it to the lerpette's `code/shared/` first, and to a library
  only after a second lerpette needs it.
- **The plate layer** (`plate.ts`): a choice about this picture. Once `sketch.image` exists the
  chapter keeps making the layer and only the drawing moves.
- **The spring and angle-spring forces:** this is the lesson. The framework makes them easy
  to see and change, never hides them.
- **The sub-step loop:** four particle chapters write it by hand and the spring chapter's text
  teaches it. It stays visible; the framework only supplies the count and size (see C1).

### Later: author tool "save this as the starting state" (G9)

The scratchpad jelly page grew an editor: pause, click masses to fix or free them, export a
JSON file (`{format: 'lerpit-jelly-setup', version: 1, picture, imageSize, mesh: {rings, spokes,
crossLinks, longLinks}, fixed: [[X, Y]...], fixedIndices, masses}`), and load it back as the
starting setup (the chapter reads `stapler-config.json` this way, rescaled by `imageSize`).

The same shape recurs whenever a starting state is easier to make by hand than to write as
numbers: placing particles, choosing fixed points, drawing an initial shape. Proposal: in the
**local view only** (gate on `isLocalView()`), the stage offers it for any chapter that
declares what is editable, and writes the file into the chapter's folder through the local
editor's existing server (`website/src/editor/server/api.ts`).

mostly in the five particles chapters, written one after another. Drift costs twice: a reader
moving between chapters relearns what a control or reading means, and the text refers to the
stage by name ("Controls › Sub-steps"), so names that drift break the text.

### C1 — the biggest one: what "Sub-steps" means

- Flow (`flow/js/index.ts:48-51`), Physical (`physical/js/index.ts:45-47`) and Spring
  (`spring/js/index.ts:41-42`) divide each frame into a fixed **number** of steps:
  `sdt = dt / s.substeps`. The step size is whatever the frame happens to be divided by.
- Soft keeps the step **size** fixed, `h = 1/(60·n)`, and takes as many steps as fit
  (`FRAME_DT = 1/60`).
- Both are labelled "Sub-steps" on the same 1–50 slider. The difference shows when the
  display refresh rate changes, since the framework steps once per display frame: at 120 Hz the
  dt/n chapters take steps half the size (different behaviour, double cost); at 30 Hz, twice
  the size (less stable).
- **Recommendation:** fixed step size everywhere. "Sub-steps" means "steps per sixtieth of a
  second", so a chapter behaves the same on a 60 Hz laptop and a 120 Hz phone. The loop stays
  visible in each chapter (it is taught); the framework only supplies the count and size:
  `const { count, h } = stepsFor(dt, s.substeps)`.
- The lesson text may need a sentence on which approach and why.

### Bugs the survey found (verified by reading the code)

- **B1 · Teleportation** (`teleportation/js/index.ts`): state `skip: 0` (line 8) but the
  slider is `min: 1, max: 10` (line 17). The solid trail is drawn only when `s.skip == 0`
  (line 35), so once the reader touches the slider, the solid trail can never come back. The
  label "Step Size" also describes something else: it counts frames skipped.
- **B2 · Live code** (`meta/live-code/code/js/src/readout.js:11`): energy is
  `0.5*v*v + 0.5*x*x`, which assumes k = 1 and m = 1, but `forces.js:2` uses `k = 8`. The
  energy shown is wrong. Also `draw.js:22` pushes to the state's history (`past.push(s.x)`),
  which the authoring guide says a view must not do. (Check the cpp variant too:
  `meta/live-code/code/cpp/src/draw.js`.)
- **B3 · Stale text:**
  - `spring/js/index.ts:44`: comment "gravity pulls it down", but no gravity is applied.
  - `teleportation/js/index.ts:5`: "A starting point: a ball on a spring. Replace it with this
    chapter's own code." — template text left in.
  - `particles/control.toml:1`: "Local only until it is ready. Switch to "published" to ship
    it." beside `status = "published"`.
  - `particles/mixtape.md:123`: "symplectic Eluer" (typo), and the text says "a wall" where the
    code draws a ceiling.

### Proposed house conventions

Write once in `docs/authoring.md`, then apply to every chapter. Each picks one variant.

1. **Sub-steps are per sixtieth of a second.** Fixed step size from `stepsFor(dt, n)`. Label
   "Sub-steps", range 1–50, placed with the integration controls. *Same behaviour on every
   display; the slider means one thing everywhere.*
2. **Energy is "Total energy".** A graph with `keepInView: 0`; add "Kinetic energy" and
   "Potential energy" only when the text discusses the split. Any chapter that conserves energy
   shows it, the three-body chapter (Physical) included. *One name for one quantity; the text
   can say "watch Total energy".*
3. **Control labels: sentence case, full words, symbol last.** "Spring constant k", "Damping
   ratio ζ", "Integration scheme", "Show the web". Order: integration, then physical
   quantities, then what is shown. *The text quotes labels; readers scan them in the same
   order everywhere.* (Note: the soft chapter's own "k" label would become "Spring constant k".)
4. **Colours from `colors.*` only, one colour per role.** Moving mass orange; fixed support
   charcoal (so the soft chapter's pinned masses become charcoal squares, not blue); spring
   blue; guides and fields gray; the reader's hand ink. No hex in chapter code, the authoring
   guide's own example included. *The palette changes in one place.*
5. **One pixel↔unit conversion, from the framework.** `ctx.input.ux/uy` for the pointer (G1)
   and `sketch.toUnits(px)` for sizes; no `PX` constants, no hand-written `px()`.
6. **Particles use one field set:** `x, y, vx, vy, fx, fy, m, r, color, trail` — `m` not
   `mass`, `color` (the sketch option's own name) not `c`. A shared `Particle` type in the
   framework. *Code moves between chapters without renaming.*
7. **Trails are sized in seconds.** `Trail.create(seconds * 60)`, ten seconds unless the
   chapter says why not. *300, 500, 600, 1000 encode no decision.*
8. **Captions: what it is, a blank line, then the law.**
   `'A mass on a spring\n\n$$F = -k(l - l_0)$$'`, LaTeX functions with a backslash (`\sin`),
   the same equation as the text. *Four formats today; two disagree with their own text.*
9. **State is a plain object;** a function only when a run must not share it; module-level
   variables only for loaded files until `ctx.loadImage` replaces them. Views never change
   state. *Restart and the code boxes rely on it.*
10. **Repeated drawings become sketch calls.** The vector field in Flow and Physical becomes
    `sketch.field(fn, { spacing })` (C6). *Copied code drifts; it already has.*

**Why nothing was applied yet:** these touch every particles chapter, and on 2026-10-23
flow, physical, spring, teleportation, mixtape.md, live-code draw.js, sketch2d.ts and theme.ts
all had the user's uncommitted edits. Confirm with the user before editing them. The bugs
(B1–B3) are independent and can be fixed first.

## 10 · How this ledger grows

After each new stage:

1. **List the workarounds:** anything the chapter does that is not its lesson — conversions,
   caches, raw three.js, manual state tracking.
2. **Ask who else will need it:** one chapter → keep it local; several chapters in one
   lerpette → `code/shared/`; several lerpettes → the framework or a library.
3. **Apply the rule from §01:** readers need it → `ctx` or `sketch`; authors only → an
   importable helper.
4. **Add a row:** tier, source stage, cost today, proposal, effort — in a new dated file.
5. **When it ships:** mark it `built` with the date and files, and add/adjust docs
   (`docs/features/<feature>/dev.md`).

## Built

- **B4 · 2D viewport had no scope (built 2026-10-23, found after the ledger was written).**
  Chapters that name the same panels share one viewport, and leaving a chapter only pauses it, so
  anything a chapter added to `sketch.scene` showed through in the next chapter. The soft
  stage's jelly appeared in the Spring and Physical chapters. Fix: `viewport2dPanel` now has a
  `scope`, like `viewport3dPanel`: each chapter gets its own scene and sketch on the shared GL
  context, emptied on a fresh run and released when the chapter goes away.
  - Files: `framework/panels/viewport2d/viewport2dPanel.ts`, the `scene` doc in `sketch2d.ts`,
    `tests/js/panelRegistry.test.ts`, and the viewport2d row in `docs/authoring.md`.
  - This makes the contract's "each run starts from an empty scene" true for 2D as well, and
    stages no longer need a `dispose` to remove their meshes.

- **G2 · latched presses, and G3 · drags past the panel's edge (built 2026-10-23).**
  - `PointerState` gains `pressed` and `released`. Each is true for the one frame after a press
    began or ended, and is cleared once a frame has advanced past it (a step and a draw saw it),
    so a click shorter than a frame shows as both in the same step.
  - The panel box captures the pointer on press, so moves and the release keep arriving outside
    the panel. `pointerleave` no longer clears `down`. `inside` is now worked out from the
    position, because a captured pointer fires no leave or enter events.
  - `pointercancel` counts as a release, once. This was the release half of G4.
  - Files: `framework/panels/contract.ts`, `framework/runtimes/createChapterRuntime.ts`, three
    tests in `tests/js/chapterRuntime.test.ts`, the `ctx.input` row in `docs/authoring.md`, and
    the soft stage, which now uses `pressed` and `released` instead of its own `wasDown`.
  - Checked in headless Chrome: dragging the jelly out of the panel and back keeps hold of it,
    and the release lands outside the panel.
  - **Still open from the proposal:**
    - `pressX`/`pressY` and `kind`;
    - G4's `touch-action: none` and first-finger-only;
    - G10 keyboard.

- **G1 · pointer in units (built 2026-10-23).**
  - `PointerState` gains `ux` and `uy`: the pointer in units, as chapters draw. The origin is
    mid-panel, x runs −1 to 1, and y points up, so one unit is half the panel's width.
  - They are computed on every pointer event from the panel box's size. A resize mid-drag is
    picked up at the next event.
  - Files: `framework/panels/contract.ts`, `framework/runtimes/createChapterRuntime.ts`, a test
    in `tests/js/chapterRuntime.test.ts`, the `ctx.input` row in `docs/authoring.md`, and the
    soft stage, whose hand-written pixel-to-unit conversion is gone.

- **G4 · touch drags without scrolling the page (built 2026-10-23).**
  - Not the proposed `touch-action: none` on the whole panel. A chapter may now define
    `grab(s, ctx)`, which runs the moment a press lands and returns whether it took hold of
    something.
  - A touch that grabbed something is kept from scrolling: `pointerdown` comes before
    `touchstart`, and a non-passive `touchstart`/`touchmove` listener calls `preventDefault`
    while holding. Every other touch scrolls the page as usual.
  - A chapter without `grab` behaves as before. Only the first finger is followed. If `grab`
    throws, the error is reported like any other and the hook is switched off.
  - The soft stage's press logic moved into `grab`. A press on the jelly (inside a triangle)
    pulls the nearest free particle, a press on the plate (an ellipse) drags the plate, and
    anywhere else grabs nothing.
  - Files: `framework/panels/contract.ts` (`grab`, `MODEL_NAMES`),
    `framework/runtimes/createChapterRuntime.ts`, three tests in `tests/js/chapterRuntime.test.ts`,
    and `docs/authoring.md` ("Dragging things").
  - Checked with touch emulation at 390 px wide: a drag on the jelly moved the page 0 px and
    pulled the jelly; a swipe on empty space scrolled the page 235 px.
  - **Possibly framework-shaped, and kept in the stage for now:** the point-in-triangle test
    and the nearest-particle pick are picking (G7).

- **Pinned controls (built 2026-10-24, asked for by the author).**
  - A control added straight to the controls card takes `pinned: true` beside its tweakpane
    params (`addBinding`, `addButton`, `addFolder`, `addBlade`). With anything pinned, the
    card's title reads "⌄ More Controls" / "⌃ Fewer Controls" and folds the rest, which open in
    the order the chapter added them. A card with
    nothing pinned is unchanged.
  - `ctx.controls()` now returns `Controls`, tweakpane's `Pane` with those four methods typed to
    take `ControlOptions`. Exported from `@lerpit/framework/chapter`.
  - When every control is pinned, folding would hide nothing, so there is no title.
  - Files: `framework/stage/chrome.ts` and `chrome.css`, the `controls` types in
    `panels/contract.ts` and `runtimes/create3DRuntime.ts`, `chapter.ts`, the `ctx.controls` row
    in `docs/authoring.md`, and the jelly stapler, which pins `k'` and "Show the web".
  - Design notes: `docs/features/pinned-controls/dev.md`.
  - **Bug found while checking it, fixed 2026-10-27:** tweakpane checkboxes were invisible on
    the stage. `--tp-input-background-color` was `var(--paper)`, the card's own face, and the box
    has no border, so "Show the web" showed a label with nothing beside it; a slider's empty
    track, drawn in the same colour, vanished too. In `stage/chrome.css`, inputs now share the
    buttons' accent ladder (`--accent-soft` at rest, `--accent-strong` on hover and focus,
    `--accent-line` when pressed), and the slider's track is drawn in the groove colour,
    `--tp-groove-foreground-color`, now `--accent-line`.
